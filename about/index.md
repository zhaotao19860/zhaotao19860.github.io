## 几件具体的事

**从零设计一套云上外网权威 DNS（京东云 ADNS，2018–2020）**
我负责整个系统的设计与开发，三个面一起做：数据面处理 DNS 协议与安全，控制面下发配置，统计分析面对运营出报表。基于 DPDK 的数据面做到**千万级 QPS、微秒级处理延迟**。但难点不在单点性能，而在三个面之间的状态一致——数据面为了性能必须把配置缓存在本地，一旦控制面下发和数据面生效之间出现偏差，用户看到的解析结果就是错的，而这种错误不会报警，只会被投诉发现。

**内网权威与外网权威是两个不同的问题（京东云 vpcdns，2020–2021）**
做完外网权威再做内网（VPC 内），我原以为是同一套东西换个部署位置。实际上内网的核心矛盾完全不同：外网的敌人是攻击流量和缓存投毒，内网的敌人是租户隔离与转发链路——同一个域名在不同 VPC 里必须解析出不同结果，而缓存和转发让这件事很容易串味。

**把配置下发和一致性校验做成可依赖的（百度云 DUDNS/MDNS，2021–2024）**
高性能数据面的代价是配置生效链路变长。MDNS 这一侧我用 Redis + MySQL 把下发做到**秒级**——MySQL 保证配置的持久与事务，Redis 承担扩散，让数据面能快速拉到最新状态。

另一半是校验。多节点权威集群里，"配置已下发"和"每个节点都在返回正确答案"之间有很大的空隙，落在里面的是静默的数据不一致：没有错误日志，没有告警，只有部分用户拿到错答案。我做的一致性监控主动向每个节点发查询、比对应答，把**问题发现时间从天级压到分钟级**。这套东西平时看不见，价值只在事故里体现。

**把转发决策下沉到交换芯片（百度 BGW/BNAT，2024– ）**
四层网关的性能天花板最终落在 CPU 上。我们探索软硬协同：用 NPL 编程 TD5，把导流这一层交给可编程交换芯片，CPU 只处理需要状态的部分。取舍很直接——芯片上能表达的逻辑有限，换来的是数量级的转发能力，代价是灵活性和调试难度。
